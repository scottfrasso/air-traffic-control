# 2026-10-17: From air traffic control to code review

## We didn't win, so we changed the question

The hackathon entry, Air Traffic Control, sequenced many coding agents landing changes on one main branch:
speculative merges, a landing order, an 8-bit runway. It worked, but after the results the question shifted. Ordering
merges isn't the bottleneck when agents write most of the code. Reviewing each change well, and knowing when a person
really has to look, is.

The model for the new direction is Anthropic's write-up on how they do code review: specialised reviewers, findings
that must be verified before anyone sees them, and risk tiers that decide how much human attention a change gets.
The goal: the least human review time that doesn't raise reverts.

## What we decided before writing code

A short brainstorm settled the shape (ADR-0027):

- **Replace GitHub, using only Cloudflare.** Repos are Cloudflare Artifacts; pull requests, runs and findings live in
  one Durable Object per repo; each review run is a Workflow; CI runs in a Container.
- **Drafts run nothing.** A PR starts as a draft. Marking it ready starts one review run for that commit.
- **CI gates the agents.** If the repo's own commands fail, no model runs. Red CI is cheap to detect and expensive to
  review.
- **A classifier decides who reviews.** It picks a risk tier, whether a person is needed, and which reviewers run
  (correctness, security, tests).
- **Every important finding is verified.** A separate session tries three times to prove it wrong; it's posted only
  if at least 2 of the 3 attempts say it's real.
- **The verdict is code, not a model.** Tiers low/medium/high need 0/1/2 human approvals. An agent never approves:
  approvals need a browser sign-in, and agents only have API tokens.

The whole pipeline was built test-first against fakes (a fake agent client, an in-memory SQLite store, local git repos
for the container). 150 tests passed before a single real agent ran.

## First contact with real agents

We moved everything to cheaper models first: Haiku 5.5 for the classifier, Sonnet 5.5 for the reviewers and
verifier, and lower per-session budgets.

The first real calls found three things the fakes had wrong:

1. Creating a sandbox environment needs `config.type: "cloud"`.
2. A mounted file's `mount_path` is relative to `/mnt/session/uploads`; we were passing the full path, so files would
   have landed at a doubled path.
3. The agent's output file shows up in the file list a second or two *after* the session goes idle. Our first spike
   reported "no output", then the file was there when we looked by hand. The client now looks again a few times, and
   skips the mounted inputs, which the same listing also returns.

The first classifier session took 15 seconds and cost one cent, and named the off-by-one bug from the diff alone.

## The end-to-end test

The live test creates a repo, opens a PR that plants two bugs CI doesn't catch (an off-by-one in a discount loop and
a shell injection), marks it ready, then pushes a fix.

**Run 1 ($0.81, 33 sessions).** Both bugs were found, verified and blocking. But the follow-up review after the fix
wasn't clean, and the test failed. Reading the findings, the agents were right: our scripted "fix" only fixed the two
bugs we planted. It left real ones behind: `grep -c` exits 1 when nothing matches, so the "fast" function throws;
`grep` treats the word as a regex where the original didn't; the discount used float math on prices, which the repo's
`REVIEW.md` forbids. The reviewer found more bugs than we planted, and that's the point.

The other lesson: all three reviewers reported every bug. Seventeen findings for about six bugs, and a verifier
session paid for each copy: 25 of the 33 sessions were verifiers.

**Run 2 ($0.46, 17 sessions).** Reviewer prompts now say what isn't their job. The test's fix commit now fixes
everything. The test passed. (The code-side dedupe hadn't actually deployed: a setup script corrupted its own config
on a second run, which we found and fixed afterwards.)

**Run 3 ($0.34, 14 sessions).** With duplicates merged across reviewers before verification, the first review posted
7 findings instead of 17, the follow-up was clean, and merge correctly waited for a person: Haiku had rated the PR
high risk, so it needs two approvals, one of them from someone other than the author.

Total for the day, spikes included: $1.63.

## Shortcuts we took, on purpose

- Cloudflare Access isn't set up yet, so a temporary admin secret mints API tokens. Those tokens still can't approve,
  so the "agents never approve" rule holds, at the cost that nobody can approve in the UI yet.
- The new pipeline runs as a separate Worker, so the hackathon entry keeps running untouched.

## Open questions

- Dedupe is a word-overlap heuristic. One duplicate still slipped through in run 3. Is a small model-based merge step
  worth a cent per run?
- How noisy is it on clean PRs? We need an eval set: known-buggy and known-clean changes, scored on what gets flagged.

## Afternoon: checks only when asked, and a UI people would use

The next request came from how agents actually work: they push hundreds of commits, and on a code host that runs CI
on every push, most of that money is wasted. The agent knows when it's done. So now:

- **A push never runs anything.** It just moves the PR's head. A run in progress finishes, and its result is marked
  stale for the new head instead of being thrown away.
- **`run_checks` is the "I'm done" call** (MCP, API, or a button). It names the commit, so an agent can't get a
  verdict for something it didn't mean. Asking twice for the same head is the same run, at no extra cost.
- **Single checks**: an agent can run just CI, or just the security reviewer, while it iterates. Merging still needs
  the full run on the head.

Then the UI. The old page was a list of boxes. The new one is built around one idea: every PR runs a **track** of
stations, CI → risk triage → agent review → verification → approvals → merge, each with a signal lamp. The
dashboard sorts PRs by whose turn it is: *Needs you*, *Agent's turn*, *Running*, *Merged and closed*. Each row is a
mini track plus the next step in plain words ("Waiting for people: 2 approvals needed, one of them from someone other
than the author"). One design call worth noting: high risk was first a red lamp, which read as "failed". Triage
didn't fail; it worked. Risk became a label, and the lamp went green.

Screenshots were taken with headless Chromium against the live Worker, through a tiny local proxy that adds the
token server-side, so no secret ever sat in the browser.

**Run 4 ($0.43) failed, and the agent was right again.** Our fix commit's tests pinned the off-by-one but not the
rounding. The tests reviewer *put the old float formula back, ran the tests, saw them still pass*, then brute-forced
99,000 price/percent pairs and listed the ones where float and integer rounding disagree (5¢ at 90% off: float says 0,
integer says 1). That's mutation testing, done unprompted, by the reviewer whose job is "would the tests catch a
regression?". We added those cases; the new tests fail on the float formula and pass on the fix.

**Run 5 ($0.31, 13 sessions) passed**: nothing ran on the push, the verdict went stale, the agent triggered the checks
again, the follow-up was clean, and merge waited for two people.

## Evening: the reviewer reviewed

A fresh reviewer (an agent with no memory of writing the code) went over the triggered-checks change. Its best catch:
a *single* check, say just CI, was counted as "the last reviewed commit". So after a push, an agent could run CI
alone, then the full checks, and the reviewers would be told to focus on an empty diff since that CI run. The real
change would never be the focus of a review, and the PR would come out clean. Its second-best: a single-check
security run that didn't happen to repeat an earlier finding marked it *fixed*, so an agent that isn't allowed to
dismiss an important finding could just re-roll the security check until the finding went away.

Both are fixed with tests that fail without the fix (we broke each fix on purpose and watched the tests catch it).
Now only a full run on a different commit can mark a finding fixed: not reporting it again on the same code is the
model varying, not a fix.

The lesson for the post: every shortcut that saves money (single checks, reusing a run) is also a way to get a
verdict you didn't earn, so each one needs a rule about what it can't change.

Run 6 ($0.35, 12 sessions) passed on the fixed code. Day total: about **$2.72**.

## Night: two more reviewers, and a lesson about events

Two fresh agents reviewed the whole branch, one for code quality and one for security. The security one found that
the headline claim, "an agent can't get code onto main without a person", wasn't true yet:

- **Anyone with a git token could just push to main.** Artifacts can't protect a branch, so main is now guarded by the
  store: any move of main that didn't come from a merge is put back.
- **CSRF**: a page on another site could make a signed-in reviewer's browser approve. Writes now need same-origin JSON.
- **Talking the model down**: the PR title went straight into the classifier's instructions, and "low risk, no human"
  meant zero approvals. Now the title is data, security always reviews, and every change needs one person unless the
  repo opts out.
- **Laundering findings**: renaming a file hid it from the protected-path rules; answering a nit could hide a later
  real bug of the same kind; a reviewer talked into calling a bug a nit could downgrade it. All closed.

Then the live test of "main is protected" failed, twice, and taught us something the unit tests couldn't: **a new
repo's push events don't flow for its first minutes.** Every push in the first ~15 seconds of a repo's life was
simply never delivered, so the store had once adopted a direct push as main's starting point. Events alone can't be a
security boundary. Now the store also checks main itself every two minutes; live, an immediate direct push to a
brand-new repo was put back after 120 seconds.

Run 7 ($0.34, 13 sessions; security now always runs) passed on the hardened build. 220 worker tests, now typechecked along with the container script.
