# 2026-10-17: From air traffic control to code review

## We didn't win, so we changed the question

The hackathon entry, Air Traffic Control, sequenced many coding agents landing changes on one main branch:
speculative merges, a landing order, an 8-bit runway. It worked, but after the results the question shifted. Ordering
merges isn't the bottleneck when agents write most of the code. Reviewing each change well, and knowing when a person
really has to look, is.

The model for the new direction is Anthropic's write-up on how they do code review: specialised reviewers, findings
that must be verified before anyone sees them, and risk tiers that decide how much human attention a change gets.
The goal: the least human review time that doesn't raise reverts.

## What we decided before writing code

A short brainstorm settled the shape (ADR-0027):

- **Replace GitHub, using only Cloudflare.** Repos are Cloudflare Artifacts; pull requests, runs and findings live in
  one Durable Object per repo; each review run is a Workflow; CI runs in a Container.
- **Drafts run nothing.** A PR starts as a draft. Marking it ready starts one review run for that commit.
- **CI gates the agents.** If the repo's own commands fail, no model runs. Red CI is cheap to detect and expensive to
  review.
- **A classifier decides who reviews.** It picks a risk tier, whether a person is needed, and which reviewers run
  (correctness, security, tests).
- **Every important finding is verified.** A separate session tries three times to prove it wrong; it's posted only
  if at least 2 of the 3 attempts say it's real.
- **The verdict is code, not a model.** Tiers low/medium/high need 0/1/2 human approvals. An agent never approves:
  approvals need a browser sign-in, and agents only have API tokens.

The whole pipeline was built test-first against fakes (a fake agent client, an in-memory SQLite store, local git repos
for the container). 150 tests passed before a single real agent ran.

## First contact with real agents

We moved everything to cheaper models first: Haiku 5.5 for the classifier, Sonnet 5.5 for the reviewers and
verifier, and lower per-session budgets.

The first real calls found three things the fakes had wrong:

1. Creating a sandbox environment needs `config.type: "cloud"`.
2. A mounted file's `mount_path` is relative to `/mnt/session/uploads`; we were passing the full path, so files would
   have landed at a doubled path.
3. The agent's output file shows up in the file list a second or two *after* the session goes idle. Our first spike
   reported "no output", then the file was there when we looked by hand. The client now looks again a few times, and
   skips the mounted inputs, which the same listing also returns.

The first classifier session took 15 seconds and cost one cent, and named the off-by-one bug from the diff alone.

## The end-to-end test

The live test creates a repo, opens a PR that plants two bugs CI doesn't catch (an off-by-one in a discount loop and
a shell injection), marks it ready, then pushes a fix.

**Run 1 ($0.81, 33 sessions).** Both bugs were found, verified and blocking. But the follow-up review after the fix
wasn't clean, and the test failed. Reading the findings, the agents were right: our scripted "fix" only fixed the two
bugs we planted. It left real ones behind: `grep -c` exits 1 when nothing matches, so the "fast" function throws;
`grep` treats the word as a regex where the original didn't; the discount used float math on prices, which the repo's
`REVIEW.md` forbids. The reviewer found more bugs than we planted, and that's the point.

The other lesson: all three reviewers reported every bug. Seventeen findings for about six bugs, and a verifier
session paid for each copy: 25 of the 33 sessions were verifiers.

**Run 2 ($0.46, 17 sessions).** Reviewer prompts now say what isn't their job. The test's fix commit now fixes
everything. The test passed. (The code-side dedupe hadn't actually deployed: a setup script corrupted its own config
on a second run, which we found and fixed afterwards.)

**Run 3 ($0.34, 14 sessions).** With duplicates merged across reviewers before verification, the first review posted
7 findings instead of 17, the follow-up was clean, and merge correctly waited for a person: Haiku had rated the PR
high risk, so it needs two approvals, one of them from someone other than the author.

Total for the day, spikes included: $1.63.

## Shortcuts we took, on purpose

- Cloudflare Access isn't set up yet, so a temporary admin secret mints API tokens. Those tokens still can't approve,
  so the "agents never approve" rule holds, at the cost that nobody can approve in the UI yet.
- The new pipeline runs as a separate Worker, so the hackathon entry keeps running untouched.

## Numbers

| | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Sessions | 33 | 17 | 14 |
| Cost | $0.81 | $0.46 | $0.34 |

| Wall time | ~4 min | ~3.5 min | ~4 min |

## Open questions

- Dedupe is a word-overlap heuristic. One duplicate still slipped through in run 3. Is a small model-based merge step
  worth a cent per run?
- How noisy is it on clean PRs? We need an eval set: known-buggy and known-clean changes, scored on what gets flagged.
